# Baza Service — каса і управлінський облік СТО

Веб-застосунок (PWA) для обліку готівки, боргів клієнтів, P&L і основних засобів СТО «База Сервіс».
Працює з телефона як звичайна програма (іконка на головному екрані), у тому числі **без інтернету**.

- **Адреса:** https://bazaservice.github.io
- **Код:** цей репозиторій (`BazaService/bazaservice.github.io`), публікується через GitHub Pages з гілки `main`.
- **Дані:** Firebase, проєкт `baza-service` (Firestore + Authentication), власник — Google-акаунт Вадима.

> ⚠️ Репозиторій **публічний**. Сюди не можна класти дані, резервні копії, ключі доступу (service account) чи паролі.
> `firebase-config.js` — публічна адреса проєкту, це не секрет; захист даних — у `firestore.rules`.

## Файли

| Файл | Що це |
|---|---|
| `index.html` | Увесь застосунок: розмітка, стилі і логіка в одному файлі. Блок розрахунків позначено коментарями `/*LOGIC*/ … /*ENDLOGIC*/` |
| `firebase-config.js` | Параметри підключення до Firebase |
| `firestore.rules` | Правила безпеки бази. **Не застосовуються автоматично** — після зміни їх треба вставити вручну: Firebase → Firestore Database → Rules → Publish |
| `sw.js` | Service worker: офлайн-режим і миттєвий запуск. Константа `V` — версія кешу |
| `manifest.webmanifest`, `icon-*.png`, `apple-touch-icon.png` | Іконка й налаштування встановлення на телефон |

Бібліотеки: Firebase JS SDK 11.0.2 з `www.gstatic.com` (динамічний `import()`), шрифти Google Fonts. Збірки (build) немає — файли публікуються як є.

## Як влаштовано

### Запуск
1. `restoreSnap()` миттєво показує останні дані з `localStorage` (`bs.snap.v1`).
2. Паралельно `loadSdk()` вантажить Firebase, `onAuthStateChanged` → вхід через Google.
3. Підписки `onSnapshot` оновлюють дані; Firestore працює з офлайн-кешем (`persistentLocalCache`), записи без інтернету відправляються пізніше автоматично.
4. Обгортка `fbdb` (`doc(path).set/update/get/onSnapshot`, `collection(path).onSnapshot`) імітує старий API: `update` = `setDoc(..., {merge:true})` (глибоке злиття). Записи **не чекають** відповіді сервера (щоб працювало офлайн); помилки йдуть у подію `fb-write-error`.

### Ролі
| Роль | Бачить | Може |
|---|---|---|
| Власник (`meta/owner.uid`) | Усе | Усе, включно з налаштуваннями і правами |
| `full` — повний доступ | Усе | Усі операції, змінювати свої; без налаштувань |
| `cashier` — касир | Свою касу (`roles/main.users[uid].box`) | Операції через свою касу; без клієнтів |
| `viewer` — перегляд | Усе | Нічого |
| `none` | Нічого | Нічого (новий користувач, поки власник не дасть роль) |

Обмеження **запису** забезпечують `firestore.rules`. Обмеження **перегляду** для касира — лише в інтерфейсі.

### Структура даних (Firestore)
| Шлях | Вміст |
|---|---|
| `meta/owner` | `{uid, email, ts}` — створюється один раз першим входом |
| `config/main` | `boxes[{id,name,archived,org}]`, `categories[]`, `incomeCategories[]`, `currencies[]`, `rates{USD:число}` (ручний курс, ₴ за 1), `legacyNames{старий_id: ім'я}`, `acct{clients{id:тип}, exp{вид:рахунок}, inc{вид:рахунок}}` (облік, див. нижче) |
| `roles/main` | `users: {uid: {role, box}}` |
| `members/{uid}` | `{seen, name, email}` — хто заходив |
| `clients/{id}` | `{name, archived}` |
| `days/{YYYY-MM-DD}` | `ops: {opId: операція}` |
| `audit/{uid}` | `{last}` |
| `audit/{uid}/months/{YYYY-MM-DD}` | `e: {entryId: {ts, action: create|edit|delete, opId, before, after, by}}` — історія змін, **тільки додавання** (правила забороняють змінювати/видаляти записи). `audit/legacy/...` — історія, перенесена зі старого застосунку |
| `data/users/{uid}/prefs` | `{auditSeen}` — особисті налаштування |

**Операція:** `type` (`expense` витрата · `income` дохід · `clientIn` від клієнта · `clientOut` клієнту · `transfer` переказ · `exchange` обмін), `date`, `from`, `to` (id кас), `client`, `cur`, `amount`, `cur2`, `amount2`, `rate`, `category`, `isAsset` + `assetName` (основний засіб), `comment`, `payVia`, `deleted` (м'яке видалення), `by`, `ts`, `editedBy`, `editedTs`, `deletedBy`, `deletedTs`.

### Розрахунки (`/*LOGIC*/`)
- Залишки кас = сума `effects(op)` по всіх неудалених операціях, окремо по валютах.
- Борги клієнтів (`clientEffects`): **+** — клієнт винен нам, **−** — ми винні клієнту.
- Курс валюти: ручний з `config.rates`, інакше курс останнього обміну з гривнею.
- P&L у гривні: доходи − витрати (ОЗ окремо), за курсом на дату операції.
- Баланс = каси + нам винні − ми винні (за поточним курсом). Курсова різниця = Баланс − P&L з початку.

### Управлінський подвійний запис (`ledger`, `osv` у `/*LOGIC*/`)
- Проводки **не зберігаються** в базі — рахуються з операцій при кожному показі. Тому зміна налаштувань рахунків одразу перераховує всі звіти, і старі теж; старі записи нічого не потребують.
- План рахунків — `ACC` (номери як у плані рахунків України), порядок показу — `ACC_ORDER`.
- Рахунок каси: `301` (₴) / `302` (валюта), аналітика `box:<id>`. Клієнт: за типом `CLIENT_KINDS` (інвестор 60, покупець 36, постачальник 63, працівник 372, банк 31, інший 377 — за замовчуванням), аналітика `cli:<id>`. Вид витрат → `acct.exp` (за замовчуванням 91; «Інше» і «Основні засоби» — 949). Вид доходу → `acct.inc` (за замовчуванням 719). Аналітика `cat:<вид>`.
- Проводка: `{date, opId, day, dt:{acc,an,cur,amt}, kt:{…}, sum (₴), org, note}`. Сума в гривні — за курсом на дату операції (`opR`).
- **Валюта рахується партіями (FIFO).** Кожна партія валюти (в касі чи в боргу клієнта) пам'ятає, з якої операції прийшла і за яким курсом (напр. «27.10 Від клієнта «інвестор Армен» 150 000 $ … по 45,35»). Перший прийшов — перший пішов. Переказ між касами переносить партії з їхнім курсом і походженням. Купівля валюти — партія за фактичним курсом обміну. Витрати й доходи у валюті — за курсом дня (як у P&L).
- **Реалізована курсова різниця** — коли валюта йде (обмін, витрата, повернення боргу) за іншою вартістю, ніж прийшла: окрема проводка в 714/945 датою цієї операції, аналітика `fx:<рахунок>~<аналітика>`, у примітці по рядках: з якої партії, за яким курсом, якою операцією пішла, скільки виграли/втратили.
- **Переоцінка** (нереалізована) — у кінці, для того, що лишилось: облікова вартість партій проти поточного курсу. Примітка: партії, «У касі / Клієнт винен нам / Ми винні», курс виріс/знизився, «поки на папері».
- Примітки — кілька рядків через `\n`; екран проводок показує їх окремими рядками, останній жирним.
- Тип клієнта без налаштування визначається за назвою: містить «інвестор» → Інвестор (60), «банк» → Банк (31), інакше Інший (377). Явне налаштування в `acct.clients` завжди важливіше.
- Організації `ORGS` (Готівка, ТОВ, ФОП 3, ФОП 2): береться з каси (`boxes[].org`, за замовчуванням «Готівка»).
- `tools/check.mjs` додатково ганяє еталон з іншим курсом і дорожчим обміном і перевіряє правила нижче.
- Перевірки, що мають виконуватись завжди: Оборот Дт = Оборот Кт; сума сальдо = 0; 714 − 945 = курсова різниця з екрана «Гроші»; P&L з рахунків = P&L з початку.
- Екран `#rakhunky`: ОСВ → рахунок (аналітика) → проводки → операція. Відкривається зі Звіту, рядки P&L ведуть одразу на потрібну аналітику.
- Провалювання з усіх підсумків: «Баланс», «P&L за місяць», «P&L з початку», «Курсова різниця» (Гроші), «У касах» (Каси), «Мені винні / Я винен» (Клієнти), підсумки P&L у Звіті. Вони відкривають `#rakhunky` з фільтром `ui.acc.only` (`ACC_ONLY`: pl, inc, exp, fx, cash, cli). P&L — без 714/945, як на екрані «Гроші».
- Аналітика курсової різниці: `fx:<рахунок>~<аналітика>` — реалізована (при обміні, витраті, поверненні), `rev:<рахунок>~<аналітика>` — переоцінка залишку.
- Еталон має версію `ETALON_VER` (у `test/etalon.js`, записується в `config.etalonVer`). Якщо в базі старіша, «Перевірка» просить скинути до еталону. **Змінив дані еталону — збільш `ETALON_VER`.**

## Тестова версія
- **Адреса:** https://bazaservice.github.io/test/ — окрема база Firebase `baza-service-test`, справжні дані не чіпаються.
- Файли в `test/`: `index.html` і `sw.js` — **ті самі**, що в робочій версії; свої — `firebase-config.js`, маніфест, іконки (з позначкою «ТЕСТ») і `etalon.js`.
- Режим визначається шляхом (`/test/` → `IS_TEST`): червона смужка «ТЕСТОВА ВЕРСІЯ», екран **«Перевірка»** (`#perevirka`), кнопка **«Скинути до еталону»** (тільки власник; працює лише якщо `projectId` закінчується на `-test`).
- `test/etalon.js` — еталонні дані з круглими сумами і **очікувані результати** (`EXPECTED`). Розрахунок очікуваних значень описано коментарем угорі файлу.
- `tools/check.mjs` — автоперевірка: проганяє блок `/*LOGIC*/` на еталоні й порівнює з `EXPECTED`. Запускається на кожен push (GitHub Actions «Перевірка еталоном»).
- Кеші service worker розділені за scope (`V = 'bs-vN|' + scope`), локальний знімок даних — окремі ключі (`bs.snap.v1` / `bs.snap.test.v1`).

## Як випустити оновлення
1. Змінити **`test/index.html`** (і `test/sw.js`), опублікувати → власник перевіряє на https://bazaservice.github.io/test/ (екран «Перевірка» має бути зеленим після «Скинути до еталону»).
   - `node tools/check.mjs` має показати «Усі … показників збігаються».
   - Якщо змінились розрахунки або додались нові показники — оновити `test/etalon.js` (дані і `EXPECTED`).
1a. Перенесення в робочу робить **власник сам**: кнопка «Перенести в робочу» в тестовій версії → «Так, перенести». Кнопка запускає через GitHub API дію «Перенести тестову версію в робочу» (`.github/workflows/promote.yml`) і показує її стан. Для цього на телефоні власника один раз зберігається ключ GitHub (fine-grained token тільки на цей репозиторій, право Actions: Read and write) — у `localStorage` під `bs.ghtoken`, **ніколи не в репозиторії й не в базі**. Якщо ключ не підходить, кнопка його стирає і просить новий. Дія запускає `tools/promote.sh` (перевірка еталоном → копіює `test/index.html` і `test/sw.js` у корінь), робить commit і push, просить GitHub Pages оновити сайт. Якщо еталон не зійшовся — нічого не переносить. Запускати можуть лише люди з правом запису в репозиторій.
1b. Або вручну (так само): після слова власника «переносимо» — `tools/promote.sh` → commit → push.
2. **Збільшити** `const V` у `sw.js` і напис `версія N` в `index.html` (`id="ver"`).
3. Якщо змінювалась структура даних — нова версія **має розуміти старі записи** (вони можуть прийти пізніше з офлайн-телефонів).
4. Якщо змінювались правила — оновити `firestore.rules` і вставити їх у консоль Firebase.
5. `git push` у `main` — GitHub Pages оновлює сайт приблизно за хвилину. Користувачі бачать нову версію з **другого** запуску (перший тихо завантажує її у фоні).
6. Оновити цей README, якщо змінилась будова чи логіка.

## Доступи і безпека
- Firebase і GitHub — акаунти власника; рекомендовано двоетапний вхід і другого довіреного власника.
- Дозволені домени для входу: Firebase → Authentication → Settings → Authorized domains (`bazaservice.github.io`).
- Резервні копії даних: щоночі автоматично, у **приватному** репозиторії `BazaService/baza-service-backup` (GitHub Actions + ключ сервісного акаунта в секреті `FIREBASE_SA`). Ніколи не класти копії сюди.
